**`fireline-classify` (docs only): the byte packing is a convention, not a measured fact.** Published 0.1.0 states two packings flatly: the `f4e2m1` nibble order (low nibble = even index, inherited from `i4`/`u4`) and the 6-bit layout (four elements per three bytes, least-significant bit first), in `MxElement::pack`, `unpack` and `packed_len`, with nothing saying they were never checked. They are the KISS Draft's pin, adopted from the Unpopped lane's storage convention; OCP MX fixes neither, and they are NOT measured against CUTLASS, Mojo, Triton or hardware (KISS ROADMAP R1.26 Q4, `options-r1-26-block-scaling.md`). They may change in a breaking release. The crate docs (the first sentence of `pack`, `unpack` and `packed_len`, the crate root) and the README now say so. No code changed in `fireline-classify`.

New module `fireline_contract::op_identity`: `parse_op_identity(line, &dyn AttrSource, &dyn DtypeSource)` reads `<op>[{k=v, ...}][[role:dtype, ...]]` and declines with `IdentityDecline` (`Malformed`, `UnknownOp`, `UnknownAttr`, `DuplicateAttr`, `Incomplete`, `AttrOrder`, `BadRoleTuple`; `wire_tag()` gives KISS's `op-identity-*` tags). The ordered field names come from `AttrTable::from_json` over KISS's `op_facts.json` (`opattrs`), the dtype tokens from the existing `DtypeSource`; no table is kept in the crate. **Structure only:** the `op-identity-bad-value` decline is not produced, because a field's type, enum vocabulary and range exist in KISS only as prose in `spec/ops.md` (its reference parses the Markdown) and no corpus JSON carries them; `OpIdentity::attrs` returns the unchecked value text, and a line this accepts is structurally valid, not value-valid. Additive, not wired into `read_contract`. Verified: KISS's 43 `op_identity_vectors` (kiss 50dc005, vendored byte-identical): all 31 decidable ones (13 accept, 18 decline) decided as KISS decided them, the 12 `bad-value` ones listed by name and asserted not decided, a mutation of the incomplete check caught; tests, clippy `-D warnings`.
